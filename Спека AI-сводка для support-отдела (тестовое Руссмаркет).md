# Спека: AI-сводка для support-отдела (тестовое Руссмаркет)

Nov 24, 2026 · @Danila

## Цель и рамки

Строим Python-скрипт, который по данным CRM и рабочих чатов собирает для support-отдела сводку в Markdown. В ней каждая заявка разделена на «подтверждено в CRM» и «известно только из переписки», и для каждой есть приоритет и действие. Сдача: завтра, 25.11, 18:00.

**Что сдаём** (по формату ответа из задания):

1. Код: скрипт плюс промпт для LLM.
2. Сводку по четырём случаям (С-17, С-24, П-08, П-09).
3. Описание первого запуска в 4–6 предложениях.
4. Что проверили на практике и что ещё нужно проверить.

**Принцип решения:** LLM только разбирает текст сообщений. Приоритеты, расхождения и действия считает код по правилам. Решения принимает человек.

**Вне рамок тестового:** реальное подключение к CRM и Telegram (делаем адаптеры-заглушки на JSON-файлах), интерфейс настроек, автоматическое изменение данных в CRM.

## Архитектура

Факты из CRM идут прямо в правила. Сообщения из чатов сначала разбирает LLM, потом проверяет код, и только после этого они попадают в правила с пометкой «неподтверждено».

| Участник | Делает | Не делает |
| --- | --- | --- |
| LLM | Выжимка сообщения, роли времени, метки | Не видит CRM, не ставит приоритет, не пишет действия |
| Код | Проверка ответа LLM, сравнение с CRM, приоритет, текст действия, учёт изменений | Не меняет данные в CRM |
| Сотрудник support | Сверяет с карточкой CRM и действует | — |

## Модель данных

Все CRM (Битрикс24, amoCRM, Salesforce) отдают данные через REST в JSON, но поля у каждой свои. Поэтому задаём свою нормализованную схему заявки, а перевод из конкретной CRM делает тонкий адаптер. В тестовом один адаптер: чтение из `data/cases.json`.

```json
{
  "case_id": "П-08",
  "type": "card_delivery",
  "crm_status": "in_transit",
  "deadline": "2026-11-23T10:00",
  "confirmations": {"manager": null, "documents": null},
  "crm_updated_at": "2026-11-23T08:00",
  "chat_messages": [
    {"msg_id": "m1", "author_role": "courier", "sent_at": "2026-11-23T09:55",
     "text": "Задерживаюсь, раньше 13:00 не приеду"}
  ]
}
```

| Поле | Значения |
| --- | --- |
| `type` | `onboarding` · `offboarding` · `card_delivery` |
| `crm_status` | `pending` · `in_transit` · `accepted` · `done` |
| `deadline` | Дата-время события: первый выход, последний день, срок доставки |
| `confirmations` | `null` = в CRM нет; иначе время подтверждения |
| `author_role` | `employee` · `manager` · `courier` · `recipient` |

Источник истины один: всё, что в полях заявки, считается подтверждённым. Всё, что в `chat_messages`, неподтверждено всегда.

## LLM-слой

LLM получает одно сообщение из чата и возвращает JSON фиксированной формы. Схема не зависит от числа и вида сообщений: она задаёт только вопросы, которые мы задаём сообщению.

**Провайдер:** OpenRouter, дешёвая модель (точный ID взять из каталога OpenRouter), `temperature=0`, JSON-режим ответа. Ключ из переменной окружения `OPENROUTER_API_KEY`. Нет ключа — берём ответы из кэша `data/llm_cache.json`, чтобы проверяющий мог запустить код у себя.

**Выходная схема:**

```json
{
  "summary": "Курьер в пробке, приедет в 10:15, просит перенести клиента на 11:00",
  "quote": "Здрасте, я по заказу на 9:20, я в пробке, в 10:15 приеду, можете перенести клиента на 11",
  "times": [
    {"time": "9:20",  "role": "reference"},
    {"time": "10:15", "role": "new_eta"},
    {"time": "11:00", "role": "request"}
  ],
  "labels": ["reports_problem", "asks_action"],
  "uncertain": false
}
```

| Поле | Что значит |
| --- | --- |
| `summary` | Выжимка без приветствий, повторов и слов-паразитов. Без оценок и советов |
| `quote` | Исходный текст дословно |
| `times[].role` | `new_eta` — новое время события · `reference` — время для привязки · `request` — просьба о переносе · `other` |
| `labels` | `claims_done` · `reports_problem` · `asks_action` · `info`; несколько сразу допустимо |
| `uncertain` | Модель не уверена в разборе |

**Правила промпта** (полный текст в `prompts/extract.md`):

- Не добавлять фактов, которых нет в тексте. Не давать рекомендаций.
- Каждое время в `times` должно буквально встречаться в сообщении («11» → `11:00` допустимо).
- Сомнение в роли или метке → `uncertain: true`, не угадывать.
- В промпт передаётся тип заявки и роль автора, данные CRM — нет (чтобы модель не «сверяла» сама).

**Валидация в коде после ответа:**

1. JSON не разобрался или не совпал со схемой (pydantic) → один повтор, затем `parse_failed`.
2. `quote` не совпадает с исходником → подменяем оригиналом.
3. Время из `times` не найдено в тексте → отбрасываем, ставим `uncertain`.
4. Два и более `new_eta` → `uncertain`.

Результат кэшируется по `msg_id`: уже разобранное сообщение в LLM повторно не уходит.

## Правила

Приоритет и текст действия берутся только из этой таблицы; тексты действий написаны заранее и согласуются с support. Хранятся в `rules.yaml`, чтобы менять их без правки кода.

**Базовые правила по CRM** (`now` = время прогона):

| ID | Тип | Условие | Приоритет | Действие |
| --- | --- | --- | --- | --- |
| R1 | card\_delivery | `in_transit` и `now >= deadline` | красный | Предупредить точку, подтвердить новое время, обновить срок в CRM |
| R2 | card\_delivery | `in_transit`, до срока < 2 ч | жёлтый | Проследить доставку |
| R3 | card\_delivery | `accepted` | зелёный | Действий не требуется |
| R4 | offboarding | последний день сегодня, `manager = null` | красный | Сегодня получить подтверждение руководителя в CRM |
| R5 | onboarding | выход завтра, `documents = null` | жёлтый | Запросить документы у руководителя, загрузить в CRM сегодня |
| R6 | onboarding | выход сегодня, `documents = null` | красный | Срочно связаться с руководителем |
| R0 | любой | ни одно правило не сработало | серый | Разобрать вручную |

**Правила по чату** (работают поверх базовых):

| ID | Условие | Что добавляет |
| --- | --- | --- |
| C1 | есть `new_eta`, оно позже `deadline` | Строка «Расхождение: по CRM X, по словам автора Y»; приоритет не ниже жёлтого |
| C2 | `claims_done`, а в CRM подтверждения нет | «В чате утверждается, что сделано. Слова подтверждением не считаются» |
| C3 | `reports_problem` | Приоритет +1 ступень |
| C4 | `asks_action` | «В чате запрос, нужен ответ» + `summary` |
| C5 | `uncertain` или `parse_failed` | «Разбор неоднозначен, прочитать оригинал» + полная цитата |

**Инварианты, покрытые тестами:**

- Чатовые правила только повышают приоритет и добавляют строки. Понизить или закрыть заявку может только CRM.
- Любое новое сообщение по открытой заявке попадает в сводку, что бы ни решила модель.
- Заявка без сработавшего правила уходит в R0, а не пропадает.

**Порядок в сводке:** красный → жёлтый → серый → зелёный. Внутри цвета первыми идут уже просроченные, далее по ближайшему сроку.

## Выдача

Наружу уходит только Markdown, JSON пишется в лог. Сообщения бывают трёх видов:

| Сообщение | Когда | Содержимое |
| --- | --- | --- |
| Полная сводка | Первый прогон за день (например, 9:00) | Все открытые заявки по приоритету |
| Изменения | Повторные прогоны, только если есть что показать | Новые, закрытые, повышенные заявки; короткая история срока |
| Актуализировать | По кнопке или команде `/summary` | Новая полная сводка из текущего состояния, без вызова LLM |

**Шаблон пункта сводки:**

```markdown
🔴 **1. П-08 · Поставка карт · срок уже нарушен**
**CRM:** доставка до 10:00, статус «В пути».
**Чат (не подтверждено), курьер:** «Задерживаюсь, раньше 13:00 не приеду»
⚠️ Расхождение: по CRM 10:00, по словам курьера не раньше 13:00.
→ Предупредить точку, подтвердить новое время, обновить срок в CRM.
```

Короткое сообщение (до 200 символов) идёт цитатой, длинное идёт как `summary`, а полная цитата остаётся в логе. В изменениях пишем историю: «П-08: срок 10:00 → 13:00 → 14:30 (3-е изменение)».

**Рассмотренные варианты актуальной сводки:**

| Вариант | Плюс | Минус | Решение |
| --- | --- | --- | --- |
| Кнопка «Актуализировать» → новое сообщение | Просто сделать; история сводок сохраняется в чате | Актуальная версия не закреплена наверху | **Выбран** |
| Живая закреплённая сводка (редактируется через `editMessageText`) | Актуальное всегда наверху | Теряется история: в 12:00 не видно, какой сводка была в 10:00 | Отложен |
| Полная сводка каждый прогон | Ничего не нужно искать | Через пару часов сводку перестают читать | Отклонён |

В тестовом вывод идёт в консоль и в файл `out/summary_<время>.md`. Отправка в Telegram и кнопка описываются как интеграция, или делаются минимальным ботом, если останется время (см. план).

## Цикл, состояние и логи

Скрипт запускается раз в `interval_minutes` (по умолчанию 60; допустимо 15, 30, 120) из `config.yaml`. Для тестов есть разовый прогон с подменой времени: `python -m summary run --once --now "2026-11-23T10:00"`.

**Шаги одного прогона:**

1. Адаптер читает заявки и сообщения.
2. Новые сообщения (нет в кэше по `msg_id`) уходят в LLM, ответ проходит валидацию.
3. Правила считают приоритет, расхождения и действия по каждой заявке.
4. Результат сравнивается с прошлым состоянием из `state/state.json`.
5. Первый прогон дня → полная сводка; иначе → сообщение с изменениями или тишина.
6. Новое состояние сохраняется, записи дописываются в лог.

**Что считается изменением:** новая заявка; заявка закрыта по CRM; приоритет вырос; новое сообщение в чате; изменился срок или статус в CRM. Одно и то же изменение дважды не шлём.

**Логи** — `logs/YYYY-MM-DD.jsonl`, по строке на событие: исходное сообщение, ответ LLM до и после валидации, сработавшие правила, итоговый приоритет, модель и время. Из них собирается очередь на разбор: всё с `uncertain`, `parse_failed` и R0. Человек раз в неделю смотрит очередь и добавляет метку, роль времени или правило, а разобранные случаи попадают в тестовый набор. Логи дают базу для такого расширения; автоматического обучения в решении нет.

## Тестирование

Три уровня. Каждый даёт цифру для раздела «что проверили на практике».

**1. Четыре кейса из задания (pytest, без LLM, через кэш).** Ожидаемый результат при `now = пн 10:00`:

| Заявка | Правила | Приоритет | Позиция |
| --- | --- | --- | --- |
| П-08 | R1, C1, C3 | красный, срок нарушен | 1 |
| С-24 | R4, C2 | красный | 2 |
| С-17 | R5, C2 | жёлтый | 3 |
| П-09 | R3 | зелёный | 4 |

Плюс юнит-тесты на инварианты: чат не понижает приоритет, сообщение не теряется, время без совпадения с текстом отбрасывается, неизвестный случай уходит в R0.

**2. Синтетика: 50 сообщений.** Генерирует и разбирает **разные модели**, чтобы одна модель не валидировала сама себя. Генератор выдаёт сообщение и ожидаемую разметку (роли времени, метки). Данила выборочно проверяет разметку и исправляет её. Распределение, чтобы не получилось 50 похожих сообщений: 3 типа заявок × 4 роли авторов; длинные и короткие; опечатки; несколько времён; время словами («к обеду», «через полчаса»); сарказм.

**3. Ручные краевые случаи: около 10.** Пишем сами, они жёстче синтетики:

- «Я по заказу на 9:20, в пробке, в 10:15 приеду, перенесите клиента на 11» — три роли времени
- «Буду в 12, хотя нет, скорее в 13» — два ETA, должно уйти в `uncertain`
- «Клиент документы не прислал, позвоню ему» — `reports_problem` + `asks_action`, не `claims_done`
- «Ну да, конечно, всё привезли» (сарказм) — ожидаем `uncertain`
- Пустое сообщение, стикер, сообщение на английском

**Метрики прогона** (скрипт `eval.py` пишет таблицу в `out/eval.md`): доля верных `new_eta`; точность меток; сколько ушло в `uncertain`; **число опасных ошибок** (верное время перепутано с другим без флага `uncertain`). Цель — ноль опасных ошибок; остальное пишем как есть. Случаи, которые никак не разобрались, становятся новыми метками или правилами и попадают в ответ как находки.

## Что войдёт в ответ работодателю

Ответ следует четырём пунктам формата из задания. Формат отправки заданием не задан, поэтому делаем так: ссылка на репозиторий плюс короткий сопроводительный текст.

1. **Код и промпт.** Ссылка на репозиторий. В сопроводительном тексте три строки о разделении ролей: LLM разбирает текст, правила решают, человек действует. Таблица правил как описание «обычных правил», которое просит задание.
2. **Сводка по четырём случаям.** Реальный вывод скрипта при `now = пн 10:00`, без ручных правок. Одной строкой после неё порядок: П-08 первым, потому что срок уже нарушен и предупредить точку займёт пару минут; С-24 сразу за ним, как самый рискованный.
3. **Первый запуск, 4–6 предложений.** Черновик:
   - Скрипт читает заявки из CRM через API и сообщения из рабочих чатов через бота, а сводку публикует в чат support-отдела к 9:00 и далее шлёт только изменения.
   - Перед действием сотрудник открывает карточку в CRM: всё с пометкой «из чата» считается неподтверждённым.
   - Первые две недели сводка работает параллельно с ручным списком дел; вместе с support каждый день сверяем оба списка.
   - Считаем два числа: время на утренний разбор до и после, и случаи, которые сводка пропустила или неверно ранжировала (цель — ноль пропусков).
4. **Что проверено / что ещё проверить.** Проверено: четыре кейса, инварианты, таблица метрик на \~60 сообщениях и находки прогона. Ещё проверить: реальные поля и статусы их CRM, реальная переписка (голосовые, фото, пересланные сообщения), как сообщение привязывается к заявке, тексты действий с самим support.

**Открытый вопрос:** как сообщение из чата привязывается к номеру заявки. В тестовом привязка дана готовой; в жизни нужен отдельный чат на заявку или сопоставление по автору и точке. Упомянуть одной строкой в «что ещё проверить».
