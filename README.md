# AI-сводка для support-отдела

Скрипт собирает ежедневную сводку для support-отдела по данным CRM и рабочих чатов. По каждой заявке видно, что подтверждено в CRM, а что известно только из переписки, какой у неё приоритет и что делать дальше.

LLM только разбирает текст сообщений. Приоритет, расхождения и действие считает код по правилам из `rules.yaml`. Решение принимает человек. Подробное описание решения, сводка по четырём случаям задания и план первого запуска есть в PDF, приложенном к ответу.

## Запуск

Нужен Python 3.11 или новее.

```bash
cd support-summary
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"
.venv/bin/python -m summary run --once --now "2026-11-23T10:00"
```

Последняя команда печатает сводку по четырём случаям задания на понедельник, 10:00, и сохраняет её в `out/summary_<время>.md`. Ключ OpenRouter не нужен: разборы этих четырёх сообщений уже лежат в `data/llm_cache.json`.

Тесты:

```bash
.venv/bin/python -m pytest
```

## Команды

| Команда | Что делает |
| --- | --- |
| `python -m summary run --once` | Один прогон. Первый прогон дня начиная с `full_summary_at` (09:00 в `config.yaml`) выдаёт полную сводку, следующие только изменения или ничего, если изменений нет. До этого времени прогон молчит |
| `python -m summary run` | Прогон по расписанию раз в `interval_minutes` из `config.yaml` |
| `python -m summary summary` | Полная сводка из текущего состояния, независимо от прошлых прогонов. Состояние не меняет, поэтому следующий `run` не пропустит изменения |

`--now "ГГГГ-ММ-ДДTЧЧ:ММ"` подменяет текущее время (для `run` только вместе с `--once`). Если повторный `run --once` ничего не напечатал, значит изменений нет; полную сводку снова покажет `python -m summary summary`.

## Своё сообщение через LLM

Добавьте заявку с сообщением в `data/cases.json` и задайте ключ:

```bash
OPENROUTER_API_KEY=... .venv/bin/python -m summary run --once --now "2026-11-23T10:00"
```

Новое сообщение уйдёт в модель (`llm_model` в `config.yaml`), ответ пройдёт проверку кодом и сохранится в кэш. Без ключа новое сообщение не теряется: оно попадает в сводку с пометкой «прочитать оригинал» и полной цитатой.

## Где что лежит

| Файл | Что внутри |
| --- | --- |
| `support-summary/prompts/extract.md` | Инструкция для LLM: какой JSON вернуть по одному сообщению |
| `support-summary/rules.yaml` | Тексты действий и приоритеты правил R0–R6, шаблоны строк C1–C5. Меняются без правки кода |
| `support-summary/config.yaml` | Модель, интервал прогона, время утренней сводки, пути к данным |
| `support-summary/data/cases.json` | Заявки и сообщения. Здесь это заглушка вместо API CRM |
| `support-summary/data/llm_cache.json` | Сохранённые ответы модели по номеру сообщения |
| `support-summary/summary/rules.py` | Логика правил: условия, повышение приоритета, порядок в сводке |
| `support-summary/summary/llm.py` | Вызов модели и проверка её ответа (`validate()`) |
| `support-summary/summary/render.py` | Текст сводки |
| `support-summary/tests/` | Тесты, в том числе эталонная сводка по четырём случаям в `test_cases.py` |

Сводка, состояние и логи пишутся в `support-summary/out/`, `state/` и `logs/`. Логи (`logs/ГГГГ-ММ-ДД.jsonl`) хранят исходное сообщение, сырой ответ модели и сработавшие правила.

## Что в репозитории заглушка

- Вместо API CRM адаптер читает `data/cases.json`. Схема заявки своя, перевод из конкретной CRM делается отдельным адаптером.
- Сообщения тоже берутся из `data/cases.json`, уже привязанными к заявке.
- Сводка выводится в консоль и в Markdown-файл. Запись в CRM в виде комментария или задачи описана в PDF как следующий шаг.
